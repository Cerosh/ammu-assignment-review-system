## 2. Conventions this design must follow (extracted from Stages 1–3)

1. **Prompt file separate from code.** One `.md` file per capability, loaded
   once at import time via a `_PATH.read_text()` pattern.
2. **Structured Pydantic output** via `model.with_structured_output(Schema)`,
   never free text.
3. **SOURCE MATERIAL vs AI-GENERATED CONTEXT**, explicitly labelled as such
   in the human message, with upstream stage results always described as
   "not authoritative."
4. **Anything Python can compute deterministically, Python computes** —
   never trust the model with arithmetic or identity generation it doesn't
   need to do:
   - `ReviewIssue.id` is assigned by enumerating in Python after the call,
     not generated by the model.
   - `RubricTrajectory.estimated_grade` is computed by `grade_for_percent()`
     from a configurable boundary table; the model only ever produces a
     percentage.
5. **The literal-exact-string lesson (from Stage 1).** Abstract instructions
   like "say plainly that X cannot be determined" were unreliable in
   practice — the model sometimes left a field silently empty, sometimes
   invented content anyway. What actually worked: giving the model an exact
   required string to emit verbatim for the "cannot be determined" case, and
   testing for that literal string. This pattern is used again in Rubric
   Trajectory's "no rubric supplied" case and should be reused here.
6. **Category/severity taxonomies must be disambiguated explicitly in the
   field description**, not left implicit — Stage 3's `content` vs
   `accuracy` ambiguity caused a real, observed test flake until the
   description was tightened.
7. **A `_XDraft` / public model split** when some fields are model-authored
   and others are Python-computed (used by Rubric Trajectory:
   `_RubricTrajectoryDraft` → `RubricTrajectory` adds `estimated_grade` and
   `grade_boundaries_used` afterward). This keeps the LLM-facing schema
   honest — it is never shown fields it isn't meant to fill in.
8. **`*_live.py` test files, skipped without `OPENAI_API_KEY`,** verify real
   model behaviour that a fake model can't exercise; offline tests verify
   wiring and guardrail text. Live test files that call a multi-stage
   pipeline share one result across tests via a module-scoped fixture.
9. **Real-data validation is mandatory**, not optional — every prior stage
   found at least one real defect only visible against real assignment/work
   data, never caught by offline tests alone.

## 3. What Stage 4 is (and is not)

Stage 3 is the **diagnostic reviewer**: "what is wrong or missing?" — it can
surface many issues, all valid, all structured, all traceable.

Stage 4 is the **prioritizer/coach**: "what should Ammu work on **first**?"
It does not re-review the work. It takes Stage 3's (and Rubric Trajectory's)
output as raw material and makes exactly one editorial decision: which
single thing matters most right now, and how to get Ammu thinking about it
without doing the thinking for her.

This maps directly onto `.ai/JSON_SCHEMA.md`'s original `PriorityImprovement`
sketch (`issueId`, `priority`, `title`, `reason`, `studentAction`) — Stage 4
is a fuller, single-item realization of that idea, extended with the
trajectory linkage and coaching guardrails that weren't in the original
sketch (written before the north star / no-answer-writing rules were
formalized in Stages 1–3).

## 4. Proposed public API

```python
async def review_priority_coach(
    assignment: str,
    student_work: str,
    rubric: Optional[str] = None,
    teacher_instructions: Optional[str] = None,
    assignment_understanding: Optional[AssignmentUnderstanding] = None,
    success_criteria: Optional[RubricSuccessCriteria] = None,
    student_work_review: Optional[StudentWorkReview] = None,
    rubric_trajectory: Optional[RubricTrajectory] = None,
    model: Optional[BaseChatModel] = None,
) -> PriorityCoach:
    ...
```

This matches the shape given exactly, and matches Stage 3's own signature
pattern (`assignment`, `student_work` required; everything else optional
context; `model` last for test injection).

**Source material vs AI-generated context**, made explicit in the human
message template with the same section-header style Stages 1–3 already use:

```
# Assignment / Task Sheet          <- source material
# Marking Criteria / Rubric         <- source material
# Additional Teacher Instructions   <- source material
# Ammu's Submitted Work             <- source material

# Stage 1 Assignment Understanding (AI-generated context -- not authoritative)
# Stage 2 Rubric Success Criteria  (AI-generated context -- not authoritative)
# Stage 3 Student Work Review       (AI-generated context -- not authoritative)
# Rubric Trajectory                 (AI-generated context -- not authoritative)
```

Stage 3's review is included as context here (unlike Rubric Trajectory,
which deliberately does *not* consume Stage 3's output because it's an
independent re-assessment) — Stage 4 explicitly *requires* Stage 3's issues
to prioritize among, so this is the first capability that chains off
Stage 3's actual result rather than just the raw rubric.

## 5. Proposed structured output schema

```python
class CriterionRef(BaseModel):
    """A rubric criterion identity, reused wherever a criterion needs to be
    referenced without repeating this shape."""
    criterion_code: Optional[str] = None   # e.g. "5.3"; None if the rubric has no codes
    criterion_name: str                     # verbatim from the rubric


class _PriorityCoachDraft(BaseModel):
    """What the model produces. current_grade/target_grade are NOT here --
    they're computed in Python from the supplied RubricTrajectory, exactly
    like estimated_grade is computed from a percent, never asked of the
    model."""

    priority_issue_id: Optional[str]
    # References one of student_work_review.issues[i].id (e.g. "S3-ISSUE-4"),
    # ONLY if the chosen priority corresponds to a specific listed Stage 3
    # issue. None if no student_work_review was supplied, or the priority is
    # a broader pattern not tied to one specific issue. VALIDATED in Python
    # after the call -- see section 9.

    priority_statement: str
    # A self-contained one/two-sentence statement of the ONE priority --
    # must make sense even if priority_issue_id is None.

    priority_category: Literal["content","evidence","analysis","accuracy","structure","grammar","rubric"]
    # Reuses Stage 3's ReviewIssue.category enum (no new taxonomy). If
    # priority_issue_id resolves to a real issue, this is OVERWRITTEN in
    # Python from that issue's actual category -- the model's own value is
    # only trusted when there's no matching issue to defer to.

    why_this_matters: str
    # Grounded in the task/rubric -- why THIS, specifically, not a generic
    # "this is important" statement.

    primary_criterion: CriterionRef
    also_affects_criteria: list[CriterionRef]
    # Supports "whether fixing one issue would improve multiple criteria"
    # (an explicit priority-selection factor) being visible in the output,
    # not just used silently to rank.

    trajectory_connection: str
    # Explains how addressing this priority relates to moving from the
    # current grade toward the next boundary. Must use hedged language
    # ("is likely to strengthen...") -- never a specific point/percent
    # increase. If no rubric_trajectory was supplied, must say so explicitly
    # rather than inventing a grade-boundary claim.

    student_question: str
    # THE one primary question. Enforced to end in "?" (see guardrails).

    improvement_target: str
    # Describes the QUALITY of thinking/evidence required -- never the
    # actual content of the answer. This is the single highest-risk field
    # for "answer leakage" alongside student_question.

    evidence_to_consider: list[str]
    # The KIND/DIRECTION of evidence to look for -- never a stated
    # conclusion about what that evidence shows.

    other_issues_deferred: list[str]
    # Acknowledges other things exist without detailing them -- prefer
    # referencing other S3-ISSUE-N ids when available, otherwise a short
    # label. Deliberately NOT a full re-review.

    confidence: Literal["low","medium","high"]

    limitations: list[str]
    # e.g. no rubric supplied, no Stage 3 review supplied so no issue could
    # be referenced, no rubric_trajectory supplied so no boundary framing
    # was possible, or the model's chosen issue id didn't match any known
    # Stage 3 issue (added by Python, see section 9).


class PriorityCoach(_PriorityCoachDraft):
    """Public result: the model's draft plus grade-boundary context computed
    in Python, exactly like RubricTrajectory.estimated_grade."""

    current_grade: Optional[str] = None
    target_grade: Optional[str] = None
    # Both computed in Python from the supplied rubric_trajectory (see
    # section 8) -- never asked of the model. None if rubric_trajectory
    # wasn't supplied, or its own estimated_grade was None.
```

### Differences from the sketch you proposed, and why

| Proposed | Decision | Reason |
|---|---|---|
| `priority_severity: str` | **Removed** | Redundant once something is *the* selected priority — restating a severity level (e.g. "medium") for the one thing already singled out as most important reads as confusing, not informative. `confidence` already conveys how sure the system is. |
| `rubric_connection: str` (prose) | **Replaced** with `primary_criterion: CriterionRef` + `also_affects_criteria: list[CriterionRef]` | Every other stage represents criterion identity as a structured code+name pair (`RubricAssessment`, `CriterionTrajectory`), never buried in a sentence. A structured ref is directly cross-referenceable by a future revision loop without re-parsing text, and naturally supports the "affects multiple criteria" priority-selection factor as a real field instead of prose. |
| `rubric_connection`/`trajectory_connection` free strings only | **Added** `current_grade`/`target_grade` (Python-computed, not in the model-facing schema) | Same reasoning as `RubricTrajectory.estimated_grade`: grade-boundary math is exactly the kind of thing that must never be left to the model, per your own instruction that "the system must not manufacture mathematical certainty." The model only ever writes the qualitative `trajectory_connection` prose; the actual boundary labels are deterministic. |
| (implicit) | **Added** `CriterionRef` as a small reusable model | Avoids repeating a 2-field shape inline twice (`primary_criterion`, `also_affects_criteria`) and mirrors existing per-criterion identity patterns. |
| (implicit) | **Added** `_PriorityCoachDraft` / `PriorityCoach` split | Same reason as `_RubricTrajectoryDraft`/`RubricTrajectory` — keeps Python-computed fields out of what's sent to the model. |

Everything else in your sketch (`priority_issue_id`, `priority_statement`,
`priority_category`, `why_this_matters`, `student_question`,
`improvement_target`, `evidence_to_consider`, `other_issues_deferred`,
`confidence`, `limitations`) is kept as proposed, in the same spirit.

## 6. Prompt design (`prompts/04_priority_coach.md`)

Structure mirrors Stages 1–3 exactly:

- **ROLE** — "You are the fourth stage... a demanding but supportive
  academic coach, not a writer." Explicitly: Stage 3 already found the
  issues; your job is to choose ONE and coach Ammu through it.
- **NORTH STAR** — same block used in Stage 3 and Rubric Trajectory
  (verbatim reuse of the "never write/rewrite/supply a replacement
  sentence" list), plus the two example pairs from your spec (prefer "What
  evidence could you use to decide whether the DVO was actually effective?"
  over "The DVO was ineffective because...").
- **CORE PRINCIPLE** — ground everything in the supplied Stage 3 issues,
  rubric, and trajectory; never invent a new issue Stage 3 didn't surface,
  never invent rubric requirements.
- **INPUT** — the 8 inputs, explicitly split into SOURCE MATERIAL and
  AI-GENERATED CONTEXT (not authoritative) sections, matching section 4.
- **YOUR TASK**, numbered exactly to the 7 things the student should leave
  knowing, each phrased as an instruction to the model:
  1. Select the single most important weakness/opportunity — considering
     impact on rubric performance, severity, whether it affects a
     high-value/foundational criterion, whether fixing it could move the
     trajectory toward the next boundary, whether it's a fundamental
     reasoning/analysis weakness vs a surface issue, whether the student can
     realistically act on it, and whether it's already adequately addressed.
     **Explicitly instructed:** do not default to the most severe-sounding
     issue if a more foundational analytical weakness exists; do not
     prioritize grammar/spelling over a major analytical weakness *unless* a
     factual/legal accuracy issue could invalidate the argument itself.
  2. Explain why it matters, tied to the task/rubric.
  3. Identify which rubric criterion (or criteria) it affects.
  4. Describe the thinking Ammu needs to do (not the answer).
  5. Write ONE question meeting the question guardrails (section 8).
  6. Describe what improvement would look like (quality of thinking/evidence
     required, never the content).
  7. Explain why this beat the other issues — this becomes part of
     `priority_statement`/`why_this_matters`, and `other_issues_deferred`
     names what didn't win without re-reviewing it.
- **IMPORTANT RULE** — the exact no-answer-writing list from your spec,
  plus the two "good vs bad" example pairs for both the question and the
  improvement target, taken directly from your instructions.
- **PRIORITY SELECTION LOGIC** — spelled out as an explicit ranked list of
  considerations (not left implicit), ending with: "If several issues seem
  similarly important, prefer whichever one blocks the most other analysis,
  or affects the highest-value criterion. Explain your reasoning in
  `why_this_matters` — a hidden decision is not acceptable."
- **HANDLING MISSING INFORMATION** — mirrors Stage 3/Trajectory precedent:
  - No `student_work_review` supplied → `priority_issue_id` must be `None`
    (there is nothing to reference), and prioritization falls back to the
    rubric/assignment/student work directly; state this in `limitations`.
  - No `rubric`/`success_criteria` → `primary_criterion.criterion_name`
    states plainly that no rubric was supplied (same literal-string
    approach as Stage 1/Trajectory), `criterion_code=None`.
  - No `rubric_trajectory` → `trajectory_connection` must say boundary
    framing isn't available, verbatim-style, rather than inventing one.

## 7. Priority-selection logic (explicit, not left to vibes)

The prompt will state the ranked considerations explicitly (this is the
single most important part of the design per your instructions, so it
should not be implicit prompt "spirit" — it should be a literal checklist
the model works through):

1. **Foundational analytical/reasoning weaknesses outrank surface issues**
   (grammar, spelling, minor wording) by default.
2. **Exception:** a factual/legal accuracy issue that could invalidate the
   argument itself may outrank an analytical weakness, because fixing the
   analysis is pointless if it rests on a wrong fact.
3. Prefer issues that affect a **higher-value or foundational** rubric
   criterion (one many other parts of the response depend on) over an
   isolated one.
4. Prefer issues where fixing it is **plausible** for the student to act on
   now, over ones that would require research/resources not reasonably
   available.
5. Prefer issues that, if fixed, would **plausibly improve multiple
   criteria** at once (this is why `also_affects_criteria` exists as a
   visible field, not just an internal ranking signal).
6. Skip anything **already adequately addressed** — don't manufacture
   urgency where Stage 3 found strength.
7. Use `rubric_trajectory` only to *frame* the priority (how it relates to
   the next boundary) — never to override the ranking above with raw
   percentage math. A criterion sitting at 40% is not automatically the
   priority if a smaller, more foundational gap elsewhere is what's actually
   blocking analysis quality.

This list is deliberately explicit in the prompt rather than trusted to
emerge from the model's general sense of "importance" — Stage 3's
category-ambiguity flake already showed that under-specified judgment calls
are exactly where models are inconsistent.

## 8. Grade-boundary computation (Python, not the model)

```python
def next_grade_up(current_grade: Optional[str], boundaries_sorted_desc: list[GradeBoundary]) -> Optional[str]:
    """boundaries_sorted_desc is RubricTrajectory.grade_boundaries_used
    (already sorted descending by minimum percent). Returns the label one
    position above current_grade, or current_grade itself if it's already
    the top boundary (the "maintain/strengthen" case), or None if
    current_grade is None or not found."""
```

`review_priority_coach()` computes `current_grade = rubric_trajectory.estimated_grade`
and `target_grade = next_grade_up(current_grade, rubric_trajectory.grade_boundaries_used)`
**before** calling the model, and passes both into the human message as
read-only context (e.g. "Current estimated position: B. Next boundary: A.")
so the model's `trajectory_connection` prose is grounded in real,
already-computed values rather than being asked to reconstruct or restate
them. They're then attached to the final `PriorityCoach` result directly —
the model never sees or fills these two fields itself.

If `current_grade == target_grade` (already at the top boundary), the
prompt instructs the model to frame `trajectory_connection` as
strengthening/maintaining Outstanding, matching your "A → maintain/strengthen"
requirement.

## 9. Consuming Stage 3 issue IDs — validation, not blind trust

This is the one place Stage 4 must be more defensive than prior stages,
because it's not just generating a fact, it's **referencing** one that
already exists and must remain traceable for the future revision loop.

After the model call:

```python
known_ids = {issue.id for issue in student_work_review.issues} if student_work_review else set()

if draft.priority_issue_id is not None and draft.priority_issue_id not in known_ids:
    # Hallucinated/mismatched reference -- never let a dangling id leak
    # into the public result the future revision loop would trust.
    limitations.append(
        f"The model referenced issue id '{draft.priority_issue_id}', which "
        "does not match any issue in the supplied Stage 3 review; treating "
        "the priority as not tied to a specific listed issue."
    )
    priority_issue_id = None
    priority_category = draft.priority_category  # nothing to defer to
else:
    priority_issue_id = draft.priority_issue_id
    if priority_issue_id is not None:
        # Trust Stage 3's own recorded category over the model's restatement.
        matched = next(i for i in student_work_review.issues if i.id == priority_issue_id)
        priority_category = matched.category
    else:
        priority_category = draft.priority_category
```

This guarantees the future revision loop (`"Was S3-ISSUE-4 resolved?"`)
never receives a `priority_issue_id` that doesn't actually exist in the
Stage 3 review it came from — a hallucinated id here would silently break
that entire future feature, so it's caught now even though the loop itself
isn't built yet.

## 10. Guardrails against answer-writing

Layered, the same way Stage 3 layers them:

1. **Prompt-level** — the exact no-write/no-rewrite/no-replacement-sentence
   list (shared verbatim with Stage 3 and Rubric Trajectory), plus the two
   good-vs-bad example pairs for both `student_question` and
   `improvement_target` taken directly from your spec.
2. **Field-description-level** — every field most at risk of "answer
   leakage" (`student_question`, `improvement_target`,
   `evidence_to_consider`) gets an explicit description contrasting the
   good/bad pattern, not just "don't give the answer" — concrete phrasing
   the model can pattern-match against, the same technique that fixed
   Stage 1's no-rubric flake (an exact template beats an abstract rule).
3. **Hard, enforced check** — `student_question.strip().endswith("?")`,
   exactly like Stage 3's `ReviewIssue.student_question`.
4. **Heuristic checks in tests** (best-effort, not perfect — same honest
   framing as Stage 3's accuracy-hedging test): flag if `student_question`
   or `improvement_target` contains a completed causal-conclusion pattern
   ("...ineffective because...", "...demonstrates that...", "...shows that
   the law failed...") of the kind your bad examples illustrate. This can't
   catch every case, but it catches the literal patterns you specifically
   flagged as bad.

## 11. Proposed offline tests (`test_priority_coach.py`)

Fake-model wiring tests, following the established pattern:

1. Returns structured `PriorityCoach`; `current_grade`/`target_grade` come
   from Python (supplied `rubric_trajectory`), not the fake model's draft.
2. Assignment/rubric/student-work/Stage-1/2/3/trajectory text all reach the
   model (each in its own labelled section).
3. Missing everything-but-required (`rubric=None`,
   `student_work_review=None`, `rubric_trajectory=None`, etc.) handled
   without error — `priority_issue_id` forced to `None` when no
   `student_work_review` is supplied at all (checked deterministically in
   Python, no model needed for this one).
4. **Id validation**: fake model returns a `priority_issue_id` that does
   NOT exist in the supplied `student_work_review.issues` → result has
   `priority_issue_id is None` and a limitation naming the mismatch.
5. **Category override**: fake model returns a valid id but a *wrong*
   `priority_category` (mismatched from that issue's real category) →
   result's `priority_category` is silently corrected to the real one.
6. `next_grade_up()` unit tests (pure Python, no model): B→A, D→C, A→A
   (top boundary), custom boundary schemes (proving it isn't hardcoded, same
   pattern as `grade_for_percent`'s existing tests).
7. Prompt guardrail-text checks (the literal-string assertions Stage
   3/Trajectory already do).

## 12. Proposed live behavioral tests (`test_priority_coach_live.py`)

Using a **module-scoped fixture** that runs Stages 1→2→3→Trajectory→4 once
on the real Hannah Clarke case and shares it across tests (the pattern that
cut Stage 3's live suite from 173s to 33s):

1. **Priority is analytical, not grammar** — the selected priority's
   `priority_category` is NOT `"grammar"` (this is the core Hannah Clarke
   validation goal — see section 13).
2. **`priority_issue_id` (if set) is a real id** — appears in the actual
   Stage 3 review's issue ids used as input.
3. **`student_question` ends with `"?"`** and doesn't contain a
   completed-conclusion pattern (heuristic, per section 10.4).
4. **`improvement_target` doesn't contain a ready-to-submit sentence** —
   heuristic check against the specific bad-example shape ("X, so Y failed
   to Z" causal-conclusion sentences).
5. **`current_grade`/`target_grade` match independent recomputation** from
   the supplied `rubric_trajectory.estimated_grade` /
   `grade_boundaries_used` — proves the grade math really is Python's, not
   the model's, exactly like the existing Trajectory test does.
6. **Only one priority** — `other_issues_deferred` is not itself a full
   re-review (heuristic: shorter than, and doesn't restate the detail of,
   Stage 3's own `issues` list).
7. **No rubric_trajectory supplied** → `current_grade`/`target_grade` both
   `None`, `trajectory_connection` states the limitation rather than
   inventing a boundary claim.
8. **No student_work_review supplied** → `priority_issue_id` is `None`
   (enforced in Python regardless of what the model says, per test 3 in
   section 11 applied here as a live sanity check too).

## 14. Open questions / risks

1. **Id-hallucination risk (addressed above, section 9)** — the model may
   reference an issue id that doesn't exist, or the right id with a
   plausible-but-wrong category. Mitigated by Python-side validation and
   correction; flagged as a limitation rather than silently trusted.
2. **"Foundational vs severe" is a genuinely fuzzy judgment call.** Unlike
   Stage 3's category ambiguity (which had a clean fix — better
   definitions), "is this analytical gap more important than that accuracy
   issue" doesn't have a purely mechanical resolution. The design leans on
   an explicit ranked checklist (section 7) rather than a formula, and
   accepts that live-test coverage here will be more about *sanity-checking
   the category of the choice* (not grammar) than proving the *single
   objectively correct* choice — there may not be one.
3. **`also_affects_criteria` could be over-used** — a model might list every
   criterion "as a stretch" to seem thorough. Prompt should say: only
   include a criterion here if fixing the priority would *plausibly and
   directly* improve it, not just tangentially relate.
4. **Interaction with a genuinely low-information rubric** — if
   `success_criteria`/`rubric` themselves already reported limitations
   (e.g. an ambiguous criterion, per Stage 2's `ambiguous_rubric.md`
   fixture), Stage 4 needs to avoid manufacturing a confident priority
   against a criterion Stage 2 already said couldn't be pinned down. This
   should be handled by instructing the model to treat Stage 2/3's own
   stated limitations as a signal to lower `confidence`, not ignore them.
5. **Should `other_issues_deferred` reference ids or free text?** Proposed:
   prefer ids when they map cleanly to Stage 3 issues, allow short free text
   for anything that doesn't (e.g. a trajectory-only observation with no
   discrete Stage 3 issue). This is a soft field with low risk either way.
6. **Cost/latency**: the live pipeline for Stage 4 alone is 4 chained model
   calls (1→2→3→Trajectory) plus Stage 4 itself = 5. The module-scoped
   fixture pattern keeps this to one full run per test *file*, not per
   test, but it's worth noting this is the most expensive test file yet if
   it isn't shared carefully.
